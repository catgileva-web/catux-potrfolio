# Бриф проекта — портфолио Анны Ивановой (UX Designer)

## Кто это

UX/Product-дизайнер, 6 лет опыта, специализация — сложные B2B/fintech интерфейсы.
Портфолио должно выглядеть небанально и запоминаться, а не как ещё один шаблон
из конструктора.

## Визуальная концепция: "инженерная схема старой ЭВМ"

Референс: советская/западная учебная анимация про устройство вычислительных
машин — диаграммы состояний с ромбами "ДА/НЕТ", временные диаграммы-дорожки,
чёрно-белые блок-схемы с толстыми стрелками и потоками двоичного кода.

Идея переноса на сайт: процесс UX-дизайна (исследование → гипотеза → прототип
→ тест → релиз) читается как схема работы вычислительной машины — с той же
точностью и без лишних декоративных элементов.

### Токены дизайна

- **Фон:** тёмный графитовый градиент — `#4d4c44` → `#242320`
  (имитирует засвеченный кадр плёнки, не плоский чёрный)
- **Панели/блоки:** почти чёрный `#141310`
- **Текст/линии:** тёплый белый `#EDEAE0`, приглушённый `#a9a798`
- **Акцент (используется очень скупо):** тёплый янтарный `#e0973a` —
  только на "ДА"-ветках, ключевых цифрах, hover-состояниях
- **Заголовки/лейблы:** IBM Plex Sans Condensed, bold, КАПС, широкий трекинг
- **Данные/подписи/бинарный код:** IBM Plex Mono
- **Основной текст:** IBM Plex Sans, обычный

### Фирменные элементы

1. **Hero-диаграмма** — флоу-чарт с ромбами решений (ГИПОТЕЗА ЯСНА? ДА/НЕТ),
   с петлёй обратно к началу — визуализирует итеративность UX-процесса.
2. **Временная шкала** (в разделе "о себе") — горизонтальные дорожки-этапы
   проекта (Discovery → Design → Test → Handoff), как логический анализатор.
3. **Title block** — нижняя панель как штамп на инженерном чертеже
   (DRAWN BY / DOC / REV / SEC), обновляется при скролле.
4. **Двоичные разделители** между проектами — тонкая стрелка + строка бит.
5. Проекты подписаны как компоненты: PROJECT 01, 02, 03…

### Чего НЕ делать

- Не добавлять лишние яркие цвета — палитра должна оставаться почти
  монохромной, акцент — редкое исключение.
- Не переусложнять анимациями — сдержанность важнее эффектов.
- Не превращать элементы схемы в чистую декорацию без смысла — каждый
  визуальный приём должен что-то объяснять о процессе или контенте.

## Технические договорённости

- Чистый HTML/CSS/JS, без фреймворков и сборки — сайт должен открываться
  и редактироваться без специальных инструментов.
- Один файл на сущность: `css/style.css`, `js/script.js` — не возвращаться
  к инлайн-стилям в `<style>`/`<script>` внутри `index.html`.
- Все правки контента — по возможности через `content/`, чтобы не трогать
  разметку ради замены текста.
